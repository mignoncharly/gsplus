## Audit indépendant du 9 août 2026

**Méthode historique.** Extraction intégrale de la bibliothèque d’e-mails et de deux DOCX audit/juridique aujourd’hui supprimés du worktree car remplacés, via script Python (zipfile/XML, bibliothèque standard, aucun outil tiers), sans se fier au registre ordonné 25/25 ni à cette matrice. Ces anciens DOCX restent uniquement dans l’historique Git et ne sont plus des sources d’exécution. Cinq audits indépendants du code réel ont vérifié chaque exigence atomique contre le code source, le schéma Prisma, les migrations SQL et les tests. Validation locale complète puis vérification de production en lecture seule.

### Verdict global

**Non-100 %.** Sur l'ensemble des exigences atomiques des trois DOCX (23 E-xx + 2 variantes E-04A/B, 12 I-xx, 4 P0, 4 P1, UI-WA-01, REF-01, VAL-01, 6 P2, 7 LEG, plus règles transverses de déduplication/scheduler/anti-saturation), la très large majorité est **VALIDÉ-PROD** avec preuve code+test+production réelle. Deux catégories empêchent le 100 % :

1. **BLOQUÉ-PREUVE-EXTERNE (1 exigence transverse — P1-01/I-08 WhatsApp)** : le code est complet, testé (cadence 0/2/10 min, consentement, webhook signé) mais `WHATSAPP_DELIVERY_ENABLED` est à `false` en production faute d'identifiants Meta Business/WhatsApp Cloud API réels. Aucun message WhatsApp n'a jamais été livré en production. **Preuve requise du client** : un numéro WhatsApp Business vérifié, un token d'accès Meta Graph API et un identifiant de numéro de téléphone (`WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_APP_SECRET`, `WHATSAPP_WEBHOOK_VERIFY_TOKEN`) à ajouter à `backend/.env`, puis un essai réel supervisé.
2. **DÉPLOYÉ NON PROUVÉ (3 exigences — E-17/E-18/E-19 destinataire réel, E-01…E-23/I-01…I-12 preuve boîte-mail individuelle, I-09/I-11 webhook SMTP fournisseur)** : le code est déployé et testé (SMTP Zoho réellement configuré, `EMAIL_DELIVERY_ENABLED=true`), mais aucune capture fraîche de réception réelle (boîte Zoho, lien de livraison cliqué par un vrai destinataire) n'a été produite dans le cadre de cet audit — la consigne interdit d'envoyer un vrai e-mail sans autorisation explicite du client, ce qui n'a pas été demandé.

**Deux écarts réels ont été trouvés dans le code et corrigés** (voir tableau ci-dessous) : P1-04 (mentions tarifaires `description`/`deliveryLabel` non bloquantes à la publication) et NOTIF-01/critère 2 (fenêtre E-03 de 5 minutes non configurable). Un écart textuel juridique a été corrigé (LEG-02 §9, « à tout moment » → « pour l'avenir »).

**Le registre historique 25/25 était trompeur** : il classait `PLANIFIÉ` la quasi-totalité de la bibliothèque d'e-mails (E-03 à E-23, I-03 à I-12) alors que le code réel — 1947 lignes dans `backend/src/emails/notifications.ts`, 383 lignes de templates, workers de production actifs — implémentait et testait déjà ces exigences. Ce document corrige cette erreur ligne par ligne ci-dessus.
